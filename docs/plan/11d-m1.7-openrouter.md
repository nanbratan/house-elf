# M1.7 — Any OpenRouter Model, Grouped by Provider

**Goal:** Replace the nine-entry Anthropic allowlist with OpenRouter's live model
catalog — hundreds of models across dozens of providers — so any of them is
selectable, each carrying its own real capabilities (reasoning, context, pricing)
instead of the three we hand-typed for M1.5/M1.6.

**Why it exists:** `models.ts` is a hand-maintained allowlist of nine Anthropic ids.
That was right for M1's scope but stops being true the moment OpenRouter is the
transport: OpenRouter fronts 337 models from 52 providers, and Mastra's model
router resolves them under an `openrouter/` prefix (confirmed via
`provider-registry.mjs --provider openrouter`; note the id-shape wrinkle in
T1.7.0). Hand-typing that list, or its per-model capabilities, does not scale and
goes stale immediately.

**Size:** large. Nine tasks: the transport switch to OpenRouter, a server-side
catalog source and the correction of its URL, a shared-schema rewrite, a
mid-stream error fix, a grouped/searchable/pinnable picker UI, docs, pins, and two
tasks for per-model settings — a server-side contract and a settings picker of its
own. The settings now vary far too much per model to show inline the way T1.5's
picker did.

---

## Ground truth, verified live (not from memory)

Fetched `GET https://openrouter.ai/api/v1/models` directly (public, no key needed)
on **2026-08-03** and cross-checked against
`.agents/skills/mastra/scripts/provider-registry.mjs --provider openrouter`. 337
models. This is what actually exists, and it corrects several things earlier
drafts of this document assumed.

### Fields present on every entry

`id` (`"anthropic/claude-opus-5"`), `canonical_slug`, `hugging_face_id`, `name`,
`created`, `description`, `context_length`, `architecture` (`modality`,
`input_modalities`, `output_modalities`, `tokenizer`, `instruct_type`),
`pricing`, `top_provider` (`context_length`, `max_completion_tokens`,
`is_moderated`), `per_request_limits`, `supported_parameters`,
`default_parameters`, `supported_voices`, `knowledge_cutoff`, `expiration_date`,
`links`. Optional: `reasoning` (213 of 337), `benchmarks` (168), `alias_target`
(11).

**"Present" is not "non-null"** — re-measured 2026-08-03 while writing T1.7.1, and
several of these are null far more often than an earlier draft implied.
`expiration_date` is present on all 337 but non-null on only 5, and **none of
those 5 is in the past**, so the expiry filter is correct but matches nothing
today. `supported_voices` is null on 335 (not "present on 2, both empty").
`hugging_face_id` is null on 81. `architecture.instruct_type` is null on 296.
`top_provider.context_length` is null on 6 and `max_completion_tokens` on 43.
`links` is `{ details: string }`. Type every one of these as nullable.

`pricing` always has `prompt` and `completion`; the rest are genuinely sparse —
`input_cache_read` 183, `input_cache_write` 58, `overrides` 44, `web_search` 98,
`input_cache_write_1h` 21, `audio` 21, `internal_reasoning` 19, `image` 18,
`input_audio_cache` 18, `image_output` 9, `audio_output` 2. Type only `prompt` and
`completion` as required.

### No icon field, at any level — and icons are dropped

Confirmed against the full key set above, including everything nested: no model
object contains an image or logo URL. A third-party source exists
(`@lobehub/icons-static-svg`, MIT, v1.94.0, zero dependencies, 903 SVGs, no
runtime fetch) but checking it against the real provider slugs killed the idea.
It has no `main`/`module`/`exports`, so there is no icon _export_ to map to —
only file paths, meaning a wrong slug is a runtime miss with no type error. And a
direct slug-to-filename match succeeds for barely half the real provider slugs:
about seven need a hand-written alias (`x-ai` → `xai`, `z-ai` → `zhipu`,
`mistralai` → `mistral`, `moonshotai` → `moonshot`, `meta-llama` → `meta`) and
about twenty have no icon at all (`writer`, `xiaomi`, `amazon`, `allenai`,
`ibm-granite`, `thinkingmachines`, `rekaai`, `mancer`, `thedrummer`, `undi95`,
`sao10k`, `gryphe`, …).

That is a hand-maintained mapping that goes stale as OpenRouter adds providers,
plus a fallback mark on roughly 40% of the list — the same standing maintenance
cost that got privacy cut below. **Icons are dropped from this milestone.** The
picker is text-only. If they are wanted later, that is a new milestone that
argues for the cost with its eyes open.

### No privacy field, and no _sufficient_ source

There is no ZDR, retention, or training flag on the model object, and none on the
public `GET /api/v1/models/:author/:slug/endpoints` response either (its keys are
`name, model_id, model_name, context_length, pricing, provider_name, tag,
quantization, max_completion_tokens, max_prompt_tokens, supported_parameters,
status, uptime_*, supports_implicit_caching, latency_last_30m,
throughput_last_30m`).

There _is_ a partially relevant machine-readable source that earlier drafts
denied existed: `GET https://openrouter.ai/api/v1/providers` returns 101 entries
with `slug`, `name`, `privacy_policy_url`, `terms_of_service_url`,
`status_page_url`, `headquarters` and `datacenters`. Policy _links_ and a
country — not a data policy. The ZDR/retention/training status a badge would
actually need is published only as a human-typed table in OpenRouter's docs
(`docs/guides/privacy/provider-logging`), keyed by inference provider, with no API
behind it. So **privacy stays dropped** — no badge, no lookup table, no filter —
but for the accurate reason: the useful part has no source, not that nothing does.

Note also that those 101 _inference providers_ (Cerebras, Amazon Bedrock, …) are
a different namespace from the ~52 model-author slugs this milestone groups the
picker by. This document means the author slug wherever it says "provider".

### The `reasoning` object is mostly empty

Present on 213 of 337 models. Field presence _within those 213_:

| field                 | present |
| --------------------- | ------- |
| `mandatory`           | 213     |
| `default_enabled`     | 85      |
| `supported_efforts`   | 86      |
| `default_effort`      | 86      |
| `supports_max_tokens` | 8       |

Only `mandatory` is universal (`true` on 62 of them). The fully-populated case is
the minority:

```json
"reasoning": {
  "mandatory": false,
  "default_enabled": true,
  "supported_efforts": ["max", "high", "medium", "low", "minimal", "none"],
  "default_effort": "high"
}
```

127 reasoning-capable models are `{ "mandatory": false }` and nothing else. Every
field but `mandatory` is optional in the schema.

**`supported_efforts` is never `null`** — zero occurrences across all 213. When a
model has no effort levels the key is simply absent. Do not model a null case;
absent means "a plain on/off toggle, no effort levels".

### The chat-modality filter would be a no-op

All 337 entries include `"text"` in `architecture.output_modalities` (322
text-only, 11 text+image, 4 text+audio). There are no embedding, moderation or TTS
entries — the default `/models` listing is already LLM-only, and non-chat models
live behind a `?category=` parameter. An earlier draft's filter on output modality
would have removed exactly zero models. **Do not write it.**

### The `~…-latest` pointers are offered — decided 2026-08-03

11 entries carry an `alias_target` object and their ids are `~`-prefixed —
`~anthropic/claude-opus-latest` → `anthropic/claude-opus-5`, `~openai/gpt-latest`
→ `openai/gpt-5.6-sol`, `~google/gemini-flash-latest`, and so on. All 11 targets
also exist as their own entries.

An earlier draft filtered them out as duplicates. **They are not duplicates.**
Picking `~anthropic/claude-opus-latest` follows Anthropic forward on its own;
picking `anthropic/claude-opus-5` stays where you put it. Those are two different
things to want, so both are offered and `alias_target` is kept as metadata — the
picker can say what a pointer currently resolves to.

The one real cost is the grouping key: `id.split('/')[0]` yields `~anthropic`,
`~google`, `~x-ai`, `~openai`, `~deepseek`, `~moonshotai`, so six of the raw 58
"providers" are tilde artifacts and the real author count is **52**. **Strip the
leading `~` when deriving the provider slug** rather than dropping the entries —
T1.7.4, where it now feeds the provider filter rather than a grouping.

**The tilde is part of the id and must survive to the wire.** Stripping belongs
in a derived display value only. `~anthropic/claude-opus-latest` is the pointer;
`anthropic/claude-opus-latest` is not a model OpenRouter has, so a strip that
leaks into the id sent for generation turns a working selection into a 404 for
exactly the 11 entries this decision exists to keep. No code strips it today —
the schema maps `id` verbatim — so this is a constraint on T1.7.4's new code.

### What does need filtering: expired models

There is a real machine-readable deprecation signal no earlier draft mentioned:
`expiration_date` (non-null on 5 models today) — respect it. Note that none of
those 5 dates has passed, so the filter is inert as of 2026-08-03; it is there for
when one does.

### The `openrouter/*` routers — resolved

Six entries are OpenRouter's own routing products rather than models. Verified
from their live descriptions:

| id                       | what it is                                                                    |
| ------------------------ | ----------------------------------------------------------------------------- |
| `openrouter/auto`        | **Deprecated.** NotDiamond meta-model; see the section below                  |
| `openrouter/auto-beta`   | Task-aware: classifies the request, routes to the top model for that task     |
| `openrouter/fusion`      | A panel of models deliberates in parallel with web search, then synthesises   |
| `openrouter/pareto-code` | Tiered shortlist of coding models ranked by Artificial Analysis percentiles   |
| `openrouter/free`        | Picks a free model at random                                                  |
| `openrouter/bodybuilder` | Turns natural language into OpenRouter API request objects — not a chat model |

They do **not** omit their capability fields, contrary to an earlier draft: all
carry `architecture`, `context_length` and `supported_parameters` (including
`reasoning` and `reasoning_effort`). What they lack is a `reasoning` _object_ and
`top_provider` values, and their `pricing` is the sentinel `"-1"`, meaning "billed
at whatever the chosen model costs, unknowable in advance". `openrouter/free` is
priced `"0"`.

**All are offered except `openrouter/bodybuilder`**, which is excluded because it
does not speak the messages-in/text-out shape at all. Two costs come with that,
accepted knowingly: `openrouter/fusion` makes several model calls per message, and
`openrouter/free` routes to free models, which on OpenRouter generally carry
prompt logging as their price — worth knowing given privacy is not displayed.

### `X-OpenRouter-Metadata` explains a router's choice — found 2026-08-04

The response's `model` field already names the concrete model a router resolved
to, so the picker does not strictly need anything more. But sending
`X-OpenRouter-Metadata: enabled` adds an `openrouter_metadata` object carrying
the routing `strategy`, the candidate endpoints with the selected one flagged,
per-attempt statuses when fallbacks fired, and a `pipeline` array naming any
plugin that altered the request — context compression, web search, guardrails.

Two properties make it worth remembering rather than adopting now: it arrives on
the **final streaming chunk** before `[DONE]`, so it costs nothing on the hot
path, and it is **stripped from response-cache hits** by design. Useful for
answering "why did this cost that" and "was my prompt compressed" when either
question comes up; no task depends on it.

### `openrouter/auto` stays the default, though it is deprecated — decided 2026-08-04

The auto-router documentation marks `openrouter/auto` **deprecated**: it is a
NotDiamond meta-model, and OpenRouter says it "will soon be replaced" by
`openrouter/auto-beta`, which classifies the prompt into one of ~30 task types
and ranks by what the community actually spends on for that task over a trailing
7 days. OpenRouter's published benchmark has Auto Beta at 83.8% on GPQA Diamond
against Auto's 50.0%, and 74% against 34% on τ-bench Airline.

**Keeping `auto` anyway.** OpenRouter replaces the slug themselves when the
switch happens, so the id we hold keeps working and gets the better router for
free. Migrating now would buy the improvement earlier at the cost of a
user-visible id change we would have to make twice.

### `cost_tier` is a user setting for the routers — decided 2026-08-04

Both routers take a plugin object rather than a normal parameter:

```ts
plugins: [{ id: 'auto-router', cost_tier: 'medium' }];
```

| `cost_tier` | Auto `cqt` | Auto Beta cost band | Behaviour                            |
| ----------- | ---------- | ------------------- | ------------------------------------ |
| `low`       | 9          | [0, 20)             | Cheapest models                      |
| `medium`    | 7          | [20, 40)            | Lower-cost models                    |
| `high`      | 5          | [40, 60)            | Middle-cost models                   |
| `xhigh`     | 3          | [60, 80)            | Higher-cost, higher-quality models   |
| `max`       | 1          | [80, 100]           | Highest-cost, highest-quality models |

On `openrouter/auto` a tier is shorthand for the older numeric
`cost_quality_tradeoff` (0–10, 0 = quality), which is a ceiling on how expensive
a candidate may be. On Auto Beta it is a **contiguous band** instead, excluding
models cheaper than the band as well as dearer ones — so the same tier means two
different things before and after the switch above. Auto's default is `cqt=7`.

This is the only dial that changes what a router costs, so it is offered:
T1.7.7 accepts it, T1.7.8 renders it. Three things make it unlike every other
setting in those tasks, and none of them is a reason not to ship it.

- **It is not in `supported_parameters`.** It is a plugin, not a generation
  parameter, so the capability-gating rule those tasks are built on cannot see
  it. Gate it on the model id being one of the six routers instead — the only
  setting in the panel gated that way.
- **Its meaning changes under the user when the slug is swapped.** A saved
  `medium` is a price ceiling on Auto and a 20–40 percentile band on Auto Beta,
  which also rules out models that are _cheaper_. The stored value stays valid,
  the behaviour does not. The control's inline description should describe the
  tier as "how much the router is allowed to spend" rather than promising a
  specific selection rule.
- **The request shape is a root-level `plugins` array**, not a
  `providerOptions` entry, so T1.7.7's mapping step has to reach a part of the
  request body we have never written through Mastra. **Verified 2026-08-04: it
  does pass through.** `openrouter/*` model strings resolve through
  `createOpenRouter()` to `OpenRouterChatLanguageModel`, bundled in
  `@mastra/core`, whose `doStream`/`doGenerate` spread `providerOptions.openrouter`
  at the **root of the request body**. So `providerOptions: { openrouter: { plugins:
[...] } }` is the route, and it unblocks `cache_control` in
  [12a-m2.1-prompt-caching.md](12a-m2.1-prompt-caching.md) equally. Note the
  model's own `settings` also accept `plugins`, `cache_control`,
  `web_search_options` and `usage` as first-class fields, but a model-router
  string cannot reach `settings` — `providerOptions` is what we have.
  overridden per request — so an account-level change silently alters behaviour,
  and sending the tier explicitly is what makes the app's behaviour predictable.
  `allowed_models` wildcards exist too and are **out of scope**.

### The catalog should come from `/models/user` — measured 2026-08-04

T1.7.1 shipped against the public `GET /api/v1/models`. There are two better
candidates, and the numbers decide between them. Measured live against this
account, whose settings already deny prompt logging:

| endpoint           | models | auth | routers | `~…-latest` |
| ------------------ | -----: | ---- | ------- | ----------- |
| `/models`          |    338 | no   | all 6   | all 11      |
| `/models?zdr=true` |    220 | no   | **0**   | **1**       |
| `/models/user`     |    230 | yes  | all 6   | 10          |

**`?zdr=true` is the wrong filter**, and not by a little: it drops every
`openrouter/*` router, including `openrouter/auto`, which is the default
selection. It also drops 10 of the 11 `~…-latest` pointers. The routers have no
endpoint of their own to carry a ZDR guarantee, so a filter that works at the
endpoint level cannot see them. Using it would empty the picker of exactly the
entries the picker is built around.

**`/models/user` is the right one.** It is a strict subset of `/models`, and the
arithmetic is exactly `220 zdr + 16 unfilterable (6 routers + 10 pointers) − 6
free models` — the six being `:free` variants that log prompts, removed by the
account's privacy settings rather than by ZDR. So it applies the account's real
policy, keeps the routers, and needs no client-side privacy logic at all. It also
tracks the account: change a setting on the website and the app follows without a
deploy.

Two consequences to carry into the change:

- **It requires the API key.** T1.7.1's `CATALOG_URL` comment says the key is
  needed to _use_ a model, not to read the catalog. That stops being true here,
  and the comment must go with it.
- **It omits `alias_target` and `benchmarks`.** Every other key matches
  `/models` exactly. `alias_target` is currently mapped as optional metadata, so
  the schema survives, but anything that plans to _read_ it must not.

Filed as **T1.7.1b**, its own task ahead of T1.7.2, because it changes committed
T1.7.1 code and T1.7.2 is already the largest task in the milestone.

### Generation parameters vary enormously per model

`supported_parameters` is the gate for every setting in T1.7.7/T1.7.8, and it is
uneven. Counts are out of the **325 models actually offered** (measured before the
`~…-latest` pointers were kept, so read them as proportions rather than totals):

| parameter                         | models | in scope this milestone |
| --------------------------------- | ------ | ----------------------- |
| `max_tokens`                      | 317    | yes                     |
| `temperature`                     | 279    | yes                     |
| `top_p`                           | 268    | no                      |
| `tools`                           | 260    | surfaced, not settable  |
| `seed`                            | 258    | yes                     |
| `structured_outputs`              | 250    | no (M3 needs it)        |
| `frequency_penalty`               | 205    | no                      |
| `reasoning` / `include_reasoning` | 201    | yes                     |
| `presence_penalty`                | 199    | no                      |
| `top_k`                           | 182    | no                      |
| `reasoning_effort`                | 79     | yes                     |
| `verbosity`                       | 11     | yes (Anthropic only)    |

**The models most likely to be picked are the ones without a temperature.** All
51 that omit it are current frontier models — `anthropic/claude-opus-5`,
`claude-sonnet-5`, `claude-fable-5` and the whole `openai/gpt-5.6-*` family.
Every control must be gated on `supported_parameters` for the same reason the
thinking toggle is gated on `reasoning`, and the settings panel for a frontier
model will legitimately be nearly empty.

`top_p`, `top_k` and the penalties are deliberately out of scope despite good
coverage: they overlap with temperature and add rows for little gain. They are a
later addition to an existing panel, not a reason to widen this milestone.

### `default_parameters` is present but mostly null

The keys appear on most models and the values usually do not: of 325,
`temperature` is non-null on **71**, `top_p` on 52, `top_k` on 16,
`repetition_penalty` on 4. `frequency_penalty` and `presence_penalty` appear on
about two thirds and are **null on every one of them**. So it is a source for
_displaying_ a default where one exists, never a source for "the value to send".
Models with no published default rest on "provider default" and send nothing.

### Discounts are real, and not in this endpoint

Investigated 2026-08-03 because OpenRouter's own site advertises models at "50%
off". `/api/v1/models` carries no discount field at all — `pricing.overrides` is
_volume tiering_ (`min_prompt_tokens` → a higher price above a threshold), not a
sale, and must not be read as one.

The signal is `pricing.discount` on
`GET /api/v1/models/{id}/endpoints`, per provider endpoint. Verified across all
337 models: it is a fraction, not a percentage (0.494 = 49.4% off), it differs
between providers of the same model (`z-ai/glm-5.2` is 0.494 on StreamLake, 0.4 on
Decart, 0 on DeepInfra), and it goes **negative** — `xiaomi/mimo-v2.5-pro` on
StreamLake is −0.2, a markup.

**The price in `/api/v1/models` is already the discounted one.** `glm-5.2` lists
at exactly Novita's post-discount rate. So a sale is already reflected in what the
picker shows; `discount` only buys the _badge_.

Getting it in bulk is not possible: `?include=endpoints`, `?endpoints=true` and
`?expand=endpoints` are silently ignored, and `/api/v1/endpoints` and
`/api/v1/models/endpoints` are both 404. It is one request per model, ~10s for the
full catalog, and it cannot be narrowed usefully — only 17 models are free, and
discounts occur on single-provider models too (7 of 54 in a 120-model sample).

**So the catalog fetch does not do this.** If a badge is wanted, fetch the
selected model's endpoints on demand — one request, at the point the UI shows that
model's details. That is a T1.7.4/T1.7.7 display concern, not T1.7.1's, and it is
not currently a task.

### Fields checked and deliberately unused

`per_request_limits` (null on all 325), `supported_voices` (null on 335 of 337),
`tokenizer`, `instruct_type`, `hugging_face_id`, `canonical_slug` (differs
from `id` on 185 models and is _not_ what the API accepts — using it as a key is a
bug), `benchmarks` (168 have it, but `design_arena` is an empty _array_ on every
one and `artificial_analysis` covers only 117), `top_a`, `prediction`,
`parallel_tool_calls` (4 models).

`web_search_options` (14 models) is **not** a capability flag and must not be used
as one: OpenRouter's docs confirm web search works on _any_ model via `:online` or
the `web` plugin, and that field only carries `search_context_size` for native
search. Gating a web-search feature on those 14 would hide a feature that works on
all 325. Web search itself is M2.5.

Two things that do affect what the picker displays:

- **`pricing.overrides` (44 models) is tiered pricing.** `qwen/qwen3.7-flash`
  charges ~3× more above 32k prompt tokens and ~6× above 256k. A single headline
  price is a simplification — say so rather than displaying a confidently wrong
  number.
- **`context_length` and `top_provider.context_length` disagree on 33 models.**
  The former is the model's maximum, the latter what the default provider serves.
  Show `top_provider`'s when present, since that is what a request actually gets.

## Decisions (from the pre-drafting Q&A and the 2026-08-03 review)

1. **OpenRouter becomes the transport in this milestone** (T1.7.0). Earlier drafts
   assumed it but never tasked it, and nothing else here works without it.
2. **No provider icons.** Checked and cut twice — see the ground-truth section and
   T1.7.4. The picker is text-only.
3. **Privacy is dropped entirely** — no badge, no lookup table, no filter.
4. **Per-model information shown:** description, context length, pricing,
   reasoning/effort support, knowledge cutoff, and whether the model can call
   tools — all real fields, all cheap.
5. **No modality filter**, because it would remove nothing. What is filtered is
   expired models and `openrouter/bodybuilder`. The `~…-latest` pointers are kept
   — they track a moving target, which is a different thing to want from a pinned
   version, not a duplicate of one.
6. **The routers are offered**, `bodybuilder` excepted, presented outside the
   provider grouping with no price or reasoning badges, because they have neither.
7. **`openrouter/auto` is the default selection.** It is always present, so the
   default can never be a dangling id, and no model id has to be hand-typed.
   Accepted knowingly: its cost per message is not knowable in advance, and the
   thinking toggle is inert on a first visit because it carries no `reasoning`
   object.
8. **The catalog is cached in memory only** — no Postgres snapshot, no disk file.
   Reasoning in T1.7.1.
9. **Pinned/favorite models** are in scope (T1.7.6) so the user isn't searching
   the full catalog every time.
10. **Settings leave the model picker entirely.** `ModelPicker` becomes purely a
    model picker; a second trigger beside it opens a `SettingsPicker` holding
    thinking, reasoning effort, temperature, verbosity, max output tokens and
    seed. Two separate triggers, no nested submenus — reasoning in T1.7.8.
11. **Settings persist per model id** in browser storage, so each model keeps its
    own configuration. This is what forces the settings trigger to carry a
    visible summary rather than a bare icon: switching models silently swaps a
    whole settings profile, and an invisible swap is a footgun.
12. **Defaults are displayed, not sent.** Where `default_parameters` publishes a
    value it is marked as the default and an unconfigured model rests on it; where
    it does not — the majority — the control reads "provider default". Untouched
    settings are absent from the request either way, so we never invent a value.
13. **Web search is not in this milestone.** It is not a model capability, so
    nothing in the catalog gates it, and it returns `url_citation` annotations
    that need rendering against persisted messages. It becomes **M2.5**, after M2
    makes messages persistent, so citation storage is designed once.
14. **The picker groups by release month, not by provider** (decided 2026-08-04
    after evaluating OpenRouter's own picker). Provider becomes a filter instead.
    This replaces the two-level nested menu earlier drafts specified, and it is
    the reason `created` joins the schema. Reasoning in T1.7.4.
15. **The picker stays a modal**, not a dropdown. We already have a working
    `Dialog` + `Command`, and the filter row and info card want the width. Cheap
    to reverse later if it feels heavy.
16. **Capability filters are derived from the catalog, not hardcoded.** Provider
    and input modality are fixed; every other candidate renders whenever the
    catalog splits on it — some models yes, some no — with no rarity threshold.
    Candidates are limited to capabilities the app exposes. See T1.7.4.

## Tasks

### T1.7.0 — OpenRouter becomes the transport

Everything below assumes OpenRouter fronts the models. Today it does not: the
allowlist holds `anthropic/claude-*` ids resolved with `ANTHROPIC_API_KEY`, which
is the only provider key in `.env.example`. Do this first, against the existing
nine-model allowlist, and prove it works before any catalog work starts.

- Add `OPENROUTER_API_KEY` to `.env` and `.env.example`, read through `env.ts` the
  same way `ANTHROPIC_API_KEY` is.
- **Mind the two id shapes.** OpenRouter's ids already contain a slash, so the
  string Mastra's model router resolves is
  `openrouter/anthropic/claude-opus-5` while the catalog entry's `id` is
  `anthropic/claude-opus-5`. The picker's id and the router's id are not the same
  string — decide which one crosses the wire and which is derived, and say so in
  one place rather than composing the prefix ad hoc at each call site.
- Confirm the composed ids through `provider-registry.mjs --provider openrouter`
  rather than assuming the prefix composes. Verify, do not infer.
- **Done, 2026-08-03. One correction:** the prefix composes as described, but
  OpenRouter's catalog spells Anthropic versions with dots

### T1.7.3 — A mid-stream error says what actually went wrong

Filed 2026-08-04 after reproducing the behaviour end to end; reuses the number
freed when provider icons were cut. Independent of the schema rewrite, so it does
not need to wait for it.

**What was measured, not reasoned about.** `@mastra/core`'s gateway honours
`process.env.OPENROUTER_BASE_URL`, so the real server was pointed at a fake
upstream streaming OpenRouter's documented mid-stream shape — an `error` object at
the chunk root _and_ `choices[0].finish_reason: "error"`, on a connection that
already returned 200. Result: the partial text stayed on screen, and the
`role="alert"` banner appeared beneath it with **Try again**. So it does **not**
fall through as a silent stop, and `finishReason` still needs no handling.

**What is wrong is the sentence.** OpenRouter's error object carries `code: 429`;
`describeChatError` reads only `statusCode`, so a mid-stream rate limit is
categorised `unknown` and reads "Something went wrong while generating the reply."
instead of the rate-limit wording. The server log confirmed the shape:
`{ message, name: 'Error', code: 429, metadata: { error_type: 'rate_limit', provider_code } }`.

- Failing test first: drive OpenRouter's documented error object through
  `describeChatError` and assert it returns `chatErrorMessage.rateLimit`.
- Read `code` alongside `statusCode` in `statusOf`, defensively and in one place.
  Every existing category then applies to mid-stream errors for free — a 502 from
  a provider disconnect becomes `providerFault` rather than `unknown`.
- `metadata.error_type` is a typed OpenRouter code and is deliberately **not**
  read. `code` alone covers every category we show, and nothing in the client's
  sentence should be derived from provider text — the T1.6 leak rule stands.
- The existing leak assertions must keep passing: no `node_modules`, no
  `file:///`, no upstream URL, no provider error class name in the output.
- **Done, 2026-08-04.** Exactly as written: `statusOf` reads `statusCode` first
  and falls back to `code`, both only when they are numbers, so every category
  now applies mid-stream. The failing test came first and the mutation that
  stops reading `code` kills it alone.

### T1.7.4 — Searchable, filterable, date-grouped model picker

`ModelPicker.svelte` becomes purely a model picker. The thinking toggle it holds
today moves out to T1.7.8 — do not extend it here and move it later, that builds
the control twice.

**Rewritten 2026-08-04 after evaluating OpenRouter's own model picker.** The
earlier draft grouped models into a two-level provider menu. OpenRouter, who have
more experience with this exact list than we do, resolved it the other way:
**models are grouped by release month, and provider is a filter** with its own
search box. That matches what this task already admitted — 52 providers, most
holding one to three community fine-tunes, is a lot of menu for little payoff —
and it deletes the nested-menu problem entirely. A flat list with a filter row is
simpler to build, simpler to keyboard-navigate, and puts the newest models where
you can see them, which is what a personal tool is actually used for.

- **Group by release month**, newest first, with the month as a section header
  (`August 2026`, `July 2026`, …). This needs `created`, which is currently mapped
  in neither schema — see T1.7.1b and T1.7.2. Confirm its unit when mapping;
  do not assume seconds.
- **Keep the modal.** OpenRouter uses a dropdown anchored to its trigger and both
  work, but we already have a working `Dialog` + `Command` from T1.5.4, including
  a documented bits-ui workaround, and the filter row plus the info card want the
  width. Widen it rather than rebuilding it. Revisit as a dropdown later if the
  modal feels heavy — this is a cheap decision to reverse, which is why it is not
  worth agonising over now.
- **A model count beside the search box**, and it tracks the active filters — the
  full catalog reads "337 models", switching a filter on drops it. This is what
  tells you a filter is doing something before you scroll.
- **Search is still the primary path.** Matches model name and provider name, so
  typing "claude" or "anthropic" both work. **While a search is active the month
  grouping collapses to a flat ranked list** — headers fragment results into
  one-row sections and help nobody.
- **A filter row, hidden behind a funnel toggle**, closed on first open so the
  default state stays uncluttered. The funnel carries a badge with the number of
  active filters.
- **Two fixed filters**, the only two worth borrowing from OpenRouter's row:
  - **Provider** — a searchable list, replacing the old grouping. Strip the
    leading `~` when deriving the slug **for display and filtering only**; see
    the warning below.
  - **Input modality** — text / image / file / audio. Real variance, and
    `inputModalities` is already going into the schema for M4's sake.
- **The rest of the filter row is derived from the catalog, not hardcoded**
  (decided 2026-08-04). A capability toggle renders only if the data justifies
  it, which means the row maintains itself as OpenRouter's catalog moves and we
  never ship a filter that matches everything or nothing.
  - **The rule: a candidate renders when the catalog actually splits on it** — at
    least one model has it and at least one does not. Nothing else. Both ends of
    that are a dead control: a toggle every model matches filters nothing, and a
    toggle no model matches yields an empty list. **Rarity is not a reason to
    hide a filter, it is the reason to have one** — the 11 models with
    `verbosity` are exactly the ones you cannot find by scrolling. No percentage
    thresholds; there is no honest number to pick and the candidate list below
    already does the work one would be reaching for.
  - **The candidates are capabilities this app actually exposes**, not every key
    in `supported_parameters`: `reasoning`, `tools`, `temperature`,
    `reasoning_effort`, `verbosity`, and `free`. Filtering by `top_k` support
    when nothing in the app can set `top_k` is noise, and this milestone already
    ruled those parameters out of the settings panel for the same reason. This
    list, not a count, is what keeps junk filters out.
  - **`free` is derived, not a field.** OpenRouter sends no `free` flag — compute
    it as `pricing.prompt === '0' && pricing.completion === '0'` in the mapper and
    put a boolean on the shared schema, so the picker does not parse price
    strings. **Guard the routers:** their pricing is the sentinel `"-1"`, meaning
    "billed at whatever the chosen model costs", and a naive numeric check that
    treats non-positive as free would label every router free. It is the exact
    opposite — unknowable in advance.
  - `/models/user` already dropped the six `:free` variants that log prompts, so
    the free count is under 17 and possibly small. That is fine — a handful of
    free models is still worth filtering to. It disappears only if the new
    endpoint returns none at all.
- **Two of OpenRouter's filters are deliberately not built**, each for a measured
  reason. **Output modality** is a no-op because every one of our entries outputs
  text — their UI needs it because their 361 includes image and video models our
  catalog does not. **Hide Unavailable** has no source: `status` lives on

- **Pinned models** (T1.7.6) show above everything, in their own collapsible
  section.
- **Routers sit outside the month grouping**, in their own section, with no price
  or reasoning badges, because they have neither. `openrouter/auto` is the default
  selection, so this section is what a first-time visitor sees selected.
- **An info card on the focused/hovered model** carries what won't fit in a row:
  description, context length, price per million tokens, knowledge cutoff, and a
  short list of which settings that model exposes. That last part matters — with
  temperature on 279 models, effort on 79 and verbosity on 11, knowing what a
  model is configurable for _before_ selecting it saves opening the settings
  panel to find it empty.
- **A "cannot call tools" marker** on the 65 models whose `supported_parameters`
  omits `tools`. The app already ships a tool; picking one of those silently
  breaks it today with nothing on screen to explain why.
- **Still no icons**, and now for a second measured reason. OpenRouter's picker
  shows them, so the question was reopened on 2026-08-04 and closed again: their

### T1.7.7 — Per-model settings: the server contract

the client sends a narrow, validated signal and the **server** decides the
provider payload. This task widens that signal from a boolean to a settings
object without loosening the rule.

- A settings schema in `packages/shared`: optional `thinking`, `reasoningEffort`,

- **Each control carries a short description** explaining what it does and what it
  costs, inline in the panel rather than as a hover-only tooltip — a menu that
  only explains itself on hover doesn't explain itself on a keyboard.
- **Mark the default value** where `default_parameters` publishes one, and note
  that it moves per model. Where none is published — the majority — the control
  reads "provider default". Untouched settings are not sent (decision 12).
- **Persistence:** a per-model-id map in browser storage, alongside the pinned
  list and selected id. Settings for a model no longer in the catalog are dropped
  on load, silently, like pins.
- Tests: a control appears only when the model supports it; switching models
  restores that model's saved settings and restores the summary in the trigger;
  a model with `mandatory` reasoning has no off option; only `supportedEfforts`
  levels are offered; an untouched control sends nothing; settings survive a
  reload; settings stored against a model absent from a fresh catalog are dropped
  without error; the cost tier control appears on a router and on no other model.

## Definition of Done

Performed manually in a browser, against the real OpenRouter catalog (no mocked
fetch):

1. The picker opens with `openrouter/auto` selected, the routers in their own
   section, and the providers listed below them.
2. Opening a provider shows its models with names and, on hover, descriptions.
3. Searching by a provider name (e.g. "anthropic") surfaces that provider's
   models; searching by a model name works too.
4. A `~…-latest` pointer appears in its provider's group with the version it
   currently resolves to shown, and no `~`-prefixed provider group exists.
5. Pinning a model surfaces it above the grouped list; unpinning removes it;
   both survive a reload.
6. The model picker contains no settings at all. The settings trigger beside it
   shows a reasoning-capable model's thinking control and, if it exposes
   `supportedEfforts`, an effort control; a model without `reasoning` shows
   neither; a model whose `supported_parameters` omits `temperature` shows no
   temperature control.
7. Setting a temperature on one model, switching to another, and switching back
   restores it — and the settings trigger's label reflects the change both times.
8. Selecting a model outside Anthropic entirely (e.g. something under `google` or
   `openai`) and sending a message gets a real streamed response through
   OpenRouter.
9. A session still holding the old `anthropic/claude-haiku-4-5` selection in
   browser storage lands on the default instead of erroring.
10. `bun run verify` passes, including coverage thresholds.

## Notes for the executing agent

- **Believe the fetched data over this document.** The ground-truth section was
  verified live on 2026-08-03; OpenRouter's catalog changes continuously. If a
  field has changed shape by the time this is implemented, the live response is
  right and this doc needs a correction logged in PROGRESS.md, per the repo's
  working agreement.
- **The recorded test fixture will drift, and that is accepted.** A fixture of a
  continuously-changing catalog silently stops resembling live data — which is
  exactly how several wrong claims reached earlier drafts of this document.
  **Decided 2026-08-03: no live shape check.** A test that hits the endpoint only
  reports on the day it is run, so it would say nothing across the quiet months
  that are precisely when a shape change would land unnoticed — while adding a
  network-dependent test to maintain. What protects the app instead is that the
  Zod parse fails loudly: a changed shape becomes a `CatalogUnavailableError` and
  a 503 from the catalog route, not a silently short list. Re-record the fixture
  by hand whenever a later task needs a field it does not carry, and run
  `bun run prettier --write` on it after.
- **Never invent a `provider/model` string.** Every id must come from the fetched
  catalog, including in tests; use the recorded fixture. The single hand-written
  id in this milestone is `openrouter/auto`, and it is a router, not a model.
- **Privacy and icons are both out of scope, on purpose.** Neither was forgotten;
  both were checked against the real data and cut. Don't reintroduce either as a
  small addition partway through — that they looked small is the trap.
- **Web search is out of scope, on purpose** — it is
  [M2.5](12b-m2.5-web-search.md). `web_search_options` in the catalog is a
  tempting false lead; see the ground-truth section before acting on it.
- **Do not put settings back in the model picker.** T1.7.4 and T1.7.8 are
  separate components with separate triggers. If a control seems easier to drop
  into the picker mid-implementation, that is the arrangement this milestone
  exists to undo.
