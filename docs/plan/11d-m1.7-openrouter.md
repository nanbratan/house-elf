# M1.7 — Any OpenRouter Model, Grouped by Provider

**Goal:** Replace the nine-entry Anthropic allowlist with OpenRouter's live model
catalog — hundreds of models across dozens of providers — so any of them is
selectable, each carrying its own real capabilities (reasoning, context, pricing)
instead of the three we hand-typed for M1.5/M1.6.

**Why it exists:** `models.ts` is a hand-maintained allowlist of nine Anthropic ids.
That was right for M1's scope but stops being true the moment OpenRouter is the
transport: OpenRouter fronts ~337 models from ~58 providers, and Mastra's model
router already resolves any of them as `openrouter/<id>` (confirmed via
`provider-registry.mjs --provider openrouter`). Hand-typing that list, or its
per-model capabilities, does not scale and goes stale immediately.

**Size:** medium-large. Seven tasks: a server-side catalog source with a Postgres
fallback, a shared-schema rewrite, provider icons, a grouped/searchable/pinnable
picker UI, docs, and a dedicated task for the reasoning-effort control — the
settings now vary too much per model to show inline the way T1.5's picker did.

---

## Ground truth, verified live (not from memory)

Fetched `GET https://openrouter.ai/api/v1/models` directly (public, no key needed)
and cross-checked against `.agents/skills/mastra/scripts/provider-registry.mjs
--provider openrouter`. This is what actually exists, and it changes two things the
original ask assumed:

- **No icon field, at any level.** No model object contains an image/logo URL.
  Nothing in OpenRouter's own data points a CDN `<img>` at a provider. There is,
  however, an easy third-party source: `@lobehub/icons-static-svg` on npm
  (checked live — v1.94.0, actively maintained, "Popular AI / LLM Model Brand SVG
  Logo and Icon Collection", one dependency, no CDN/network call at runtime since
  it ships the SVGs). That clears the "don't over-engineer this" bar, so icons
  stay in scope — see T1.7.3.
- **No privacy field on the model object at all, and no equivalently easy source.**
  ZDR / retention / training status is published only as a human-typed table in
  OpenRouter's docs (`docs/guides/privacy/provider-logging`), keyed by
  **provider**, not by model, and there is no package or API that turns it into
  data — the only way to show it is to hand-transcribe that table ourselves and
  keep it in sync by hand as OpenRouter's docs change. That is real, standing
  complexity for a value with no easy source, so **privacy is dropped from this
  milestone entirely** — no badge, no lookup table, no filter. If it's wanted
  later, that's a new milestone with its own justification for taking on the
  maintenance cost, not a corner cut here.

Real per-model fields, present on every entry: `id` (`"anthropic/claude-opus-5"`,
provider slug is the string before the first `/`), `name`, `description`,
`context_length`, `pricing` (`prompt`/`completion` per-token, sometimes `image`,
`audio`, `web_search`, cache read/write, and an `overrides` array for
tiered/long-context pricing), `architecture.input_modalities` /
`output_modalities`, `supported_parameters` (e.g. `"reasoning"`,
`"reasoning_effort"`, `"tools"`, `"response_format"`, `"verbosity"`), and an
**optional** `reasoning` object present only on models that can think:

```json
"reasoning": {
  "mandatory": false,
  "default_enabled": true,
  "supported_efforts": ["max", "xhigh", "high", "medium", "low"],
  "default_effort": "high"
}
```

`supported_efforts` is `null` when any string is accepted, and omitted entirely
when the model has no effort levels at all (a plain on/off). A `supports_max_tokens`
boolean is also present on some models per OpenRouter's reasoning-tokens docs —
confirm its presence per entry rather than assuming it, same discipline as
everything else here.

The 337-model list also includes non-chat entries (audio, image generation,
embeddings, moderation) and deprecated aliases. These do not speak the
`messages`-in/text-out shape Mastra's agents and workflows call, so they are
filtered out at the catalog source, not hidden in the UI.

**Open question — `openrouter/auto` and `openrouter/auto-beta`:** these are
dynamic router "models" — OpenRouter itself picks the underlying model per
request based on cost/quality tradeoffs, per `docs/guides/routing/auto-router`.
They have no fixed `reasoning`, `pricing`, or `context_length` of their own (those
depend on whatever gets picked at request time), which is why the earlier draft
excluded them by default — a picker entry that can't say what it costs or
whether it thinks sits oddly next to 336 that can. That's a real difference, but
not necessarily a reason to hide a genuinely useful option. **Decide before
T1.7.1 is built:** exclude them (current default), or include them as a distinct
"Auto" entry outside the provider grouping with no capability badges shown.

## Decisions (from the pre-drafting Q&A)

1. **Icon shown at the provider level**, sourced from `@lobehub/icons-static-svg`
   (bundled, no runtime fetch). **Privacy is dropped entirely** — no easy source
   exists, and the only alternative is hand-maintained complexity for a feature
   that wasn't worth that cost.
2. **Per-model settings shown:** description, context length, pricing, and
   reasoning/effort support — all four, since they are all real fields.
3. **Catalog is fetched live and filtered to text chat models** — same reasoning
   Explore gave the user: non-chat modalities are a different API shape that
   neither the composer nor a future M5 workflow step calls the same way, so
   filtering now costs nothing later.
4. **Pinned/favorite models** are in scope (T1.7.6) so the user isn't searching
   the full catalog every time.
5. **The catalog is persisted to Postgres**, not just cached in memory, so a
   server restart during an OpenRouter outage still has something to serve
   (T1.7.1).
6. **The effort-level control has an explicit home**: T1.7.7, sequenced after the
   picker itself, in this same milestone — not an undefined "later."

## Tasks

### T1.7.1 — Server-side OpenRouter catalog fetch

- New module, e.g. `apps/server/src/mastra/openrouter-catalog.ts`. Fetches
  `GET https://openrouter.ai/api/v1/models` (no auth required for the list), maps
  each entry to the shared schema (below), and filters to chat-capable models:
  `architecture.output_modalities` includes `"text"` and the model is not a
  deprecated/dynamic alias (`openrouter/auto`, `openrouter/auto-beta` excluded
  explicitly — they omit `reasoning` and per-model capability fields entirely,
  being routers rather than models).
- **Cache it in memory, and persist it to Postgres as a fallback.** Fetching 337
  models on every chat request is wasteful and adds latency to something that
  changes rarely. Keep an in-memory cache with a TTL (propose one hour) for the
  fast path, but also write each successful fetch to a table (e.g.
  `openrouter_model_catalog`, one row per snapshot or one row overwritten per
  fetch — decide based on whether history is ever useful, and if not, don't keep
  it) so that a fresh server process during an OpenRouter outage has something
  better than a hardcoded emergency list to serve. This is genuinely needed, not
  speculative: M2 already brings Postgres into the stack, so there's no new
  infrastructure cost, only a table and a read/write path.
- **Model resolution stays validated, not trusted.** The client still sends only
  an id; the server still checks it against the last-fetched (or last-persisted)
  catalog before resolving it through Mastra, exactly as `resolveModel` does
  today — a client cannot request a model that was not in a catalog the server
  itself fetched.
- **Fetch failure must not take the chat route down.** If OpenRouter's models
  endpoint is unreachable, fall back in this order: in-memory cache (even if
  stale) → the Postgres-persisted snapshot → only then a hard failure (e.g. 503
  from the catalog route specifically). A metadata-endpoint outage must never
  block sending chat messages against a model the client already has selected.
- Tests: the fetch is mapped to the shared schema correctly (use a recorded fixture
  of a real response, not a live network call, in tests); non-chat and dynamic-alias
  entries are filtered out; the cache serves without refetching inside the TTL and
  does refetch after it; the Postgres fallback is served when the live fetch fails
  and the in-memory cache is cold; an unresolvable id after the real fetch is still
  a 400 from `resolveModel`, unchanged from today.

### T1.7.2 — Shared schema rewrite

`packages/shared/src/index.ts`'s `selectableModelSchema` is Anthropic-shaped
(`family: 'opus'|'sonnet'|'haiku'`, `thinking: 'optional'|'always'|'unsupported'`).
Replace it with a shape that matches what's real:

- `provider` (the id's slug before `/`) replaces `family` for grouping — do not
  keep a fixed enum; there are 58 of them today and no reason to hand-list them.
- `reasoning` becomes a structured optional object mirroring OpenRouter's own
  shape (`supportedEfforts: readonly string[] | null`, `defaultEffort`,
  `mandatory`, `supportsMaxTokens`) rather than the current three-state enum —
  the enum cannot express "medium/high/max only" or "mandatory, cannot disable",
  both of which are real states on real models today.
- Add `description`, `contextLength`, `pricing` (typed to the fields actually
  present — do not require ones that are sometimes absent).
- **This is a breaking schema change.** `prepareChatRequest`'s
  `wantsThinking`/`thinkingProviderOptions` and the composer's toggle both read
  the old three-state shape; they need updating in the same milestone, not left
  half-migrated. Search the whole repo for `THINKING_SUPPORT`,
  `thinkingSupportSchema`, and `MODEL_FAMILIES` before starting — every reference
  needs a decision, not just the schema file.
- Keep `id`, `label` (source it from OpenRouter's `name`), and the catalog
  envelope (`initialModelId` + `models[]`) shape.

### T1.7.3 — Provider icons

- Add `@lobehub/icons-static-svg` (confirmed on npm, actively maintained, ships
  SVGs directly — no runtime fetch, no CDN dependency). Build a small lookup from
  OpenRouter's provider slug (`anthropic`, `google`, `x-ai`, `z-ai`, …) to that
  package's icon export, since the two naming schemes won't match 1:1 for every
  provider.
- **Unknown providers must degrade, not crash or disappear.** A provider slug
  present in the live catalog with no matching icon gets a generic fallback mark
  (e.g. the provider's first letter, or a neutral placeholder) — never silently
  dropped from the list, since that would make a real, selectable model invisible.
- No privacy badge, no data-policy table. That idea is dropped for this milestone
  per the ground-truth section above — do not reintroduce it as a "quick" inline
  addition; it wasn't quick, that's why it was cut.

### T1.7.4 — Grouped, nested model picker

- Replace `ModelPicker.svelte`'s flat list with a two-level menu: providers as
  the top level (each showing its icon), models nested under their provider.
- **Description** is shown as a tooltip on hover/focus, not permanently inline —
  descriptions run to several sentences and would dominate a dense list.
  Confirm this placement is acceptable before treating it as settled; it is a
  UI call the user asked to be involved in.
- **Search matches both model name and provider name.** Typing "claude" or
  "anthropic" both need to surface Anthropic's models — filter across both
  fields, not just the model's own name/id.
- **Pinned models** (T1.7.6) show above the grouped list, ungrouped, so the
  point of pinning — not hunting through providers — is actually met.
- Keep T1.6's boolean toggle behavior for models that have `reasoning`, disable
  it for models that don't. The effort-level control itself is T1.7.7, not this
  task — see there for why it's split out.
- Tests: providers group correctly; search matches on model name and on provider
  name; keyboard navigation still reaches every model (this is bits-ui territory —
  check its nested-menu primitives before hand-rolling one); an unknown provider
  still renders with its fallback icon rather than being skipped; pinned models
  appear above the grouped list.

### T1.7.5 — Documentation

- Record the OpenRouter-catalog decision in
  [01-decisions.md](01-decisions.md): why a live fetch replaces the static
  allowlist, why privacy was dropped (no easy source) while icons were kept (one
  was found), and why the Postgres fallback exists.
- Log deviations — e.g. the `auto`/`auto-beta` decision, whatever it ends up

### T1.7.6 — Pinned / favorite models

- A model can be pinned from the picker (e.g. a pin icon next to each entry,
  reachable by keyboard, not just a hover-only mouse target).
- Pinned models render above the grouped provider list, in the order pinned or
  alphabetically — pick one and be consistent, this is a small enough call not
  to need a question back to the user, but say which was chosen in PROGRESS.md.
- **Persistence:** browser storage is enough for now, matching how the current
  model/thinking choice already persists client-side (per T1.6.1) — there is no
  user account or cross-device sync yet (that's M6), so a server-side pin table
  would be state with no way to reach it from a second device anyway.
- A pinned model that later disappears from OpenRouter's catalog (deprecated,
  removed) must not crash the picker — drop it from the pinned list silently on
  next load rather than showing a broken entry.
- Tests: pinning and unpinning updates the persisted list; pinned models appear
  above the grouped list on reload; a pinned id no longer present in a fresh
  catalog fetch is dropped without error.

### T1.7.7 — Reasoning effort control

This is its own task, not a stray follow-up, because it's a real UI decision that
the grouped-picker rework (T1.7.4) would otherwise absorb without review: once a
model is selected, and it has `reasoning.supportedEfforts` beyond a plain
on/off, the user needs a way to pick an effort level, not just toggle thinking
on.

- Where it lives is the open question this task answers: options include (a) a
  small control in the composer footer next to the thinking toggle, shown only
  when the selected model has more than an on/off, or (b) inside the model
  picker itself, as a per-model setting shown after selection. Bring both to the
  user rather than picking silently — this is exactly the kind of user-visible
  call the working agreement says to ask about.
- Respect `mandatory` (hide the disable option entirely) and `supportedEfforts`
  (only offer the levels the model actually accepts, including the `null` case
  meaning any string is accepted — pick a sane fixed set to expose for that
  case rather than a free-text field).
- Tests: the control only appears for models with more than a boolean; the sent
  request carries the chosen effort, not just a boolean; a model whose
  `reasoning` is mandatory hides the off option; switching to a model without
  `reasoning` clears/hides the control the same way T1.6.1 handles the boolean
  toggle today.

## Definition of Done

Performed manually in a browser, against the real OpenRouter catalog (no mocked
fetch):

1. The model picker opens to a list of providers, each with an icon.
2. Opening a provider shows its models with names and, on hover, descriptions.
3. Searching by a provider name (e.g. "anthropic") surfaces that provider's
   models; searching by a model name works too.
4. Pinning a model surfaces it above the grouped list; unpinning removes it;
   both survive a reload.
5. Selecting a reasoning-capable model shows the thinking toggle; a model with
   more than a plain on/off also shows the effort control from T1.7.7; selecting
   one without `reasoning` shows neither.
6. Selecting an OpenRouter model outside Anthropic entirely (e.g. something
   under `google` or `openai`) and sending a message gets a real streamed
   response through `openrouter/<id>`.
7. Stopping the server, then starting it with no network access to OpenRouter,
   still serves a model catalog from the Postgres-persisted snapshot rather than
   failing outright.
8. `bun run verify` passes, including coverage thresholds.

## Notes for the executing agent

- **Believe the fetched data over this document.** OpenRouter's catalog changes
  continuously; if a field this doc describes has changed shape by the time this
  is implemented, the live response is right and this doc needs a correction
  logged in PROGRESS.md, per the repo's working agreement.
- **Never invent a `provider/model` string.** Every id must come from the fetched
  catalog itself, filtered as described — do not hand-type any model id in this
  milestone, including in tests; use a recorded fixture from a real fetch.
- **Privacy is out of scope for this milestone, on purpose.** Don't reintroduce
  it as a small addition partway through — it was cut because there was no easy
  source, not because it was forgotten.
- Resolve the `auto`/`auto-beta` question (see Ground truth) before T1.7.1's
  filter is written — whichever way it goes, it changes what the filter excludes.
