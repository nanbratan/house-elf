# M2.6 — Image generation (stub)

**Status:** not planned in detail. This document records why the milestone exists
and what is already known, so the session that plans it properly does not start
from scratch.

**Goal:** ask for an image in a conversation, watch it arrive, and be able to look
at it, keep it, or paste it somewhere else.

## Why it is after M2.5

It is not urgent, and everything ahead of it is load-bearing for it. M2 decides how
a message is stored, and a generated image is the largest thing this app will ever
put in a message. M2.5 settles how a non-text response part is rendered and
persisted — citations first, images second — so the message-part renderer is
extended once rather than invented twice. Placing this before either means
designing message storage around an image with no persistence layer to store it in.

## Known before planning starts

Verified against OpenRouter's documentation on 2026-08-05. Everything here is
about their API, not ours; nothing has been checked against the installed
packages yet, and that is the planning session's first job.

**There are three different ways to get an image out of OpenRouter, and they are
not variations on one thing.** Choosing between them is the first decision of this
milestone, because the rest of the task list changes shape depending on it:

1. **The dedicated image endpoint.** `/api/v1/images/models` lists image models;
   generation returns `data[].b64_json` with a `media_type` (`image/png`,
   `image/svg+xml`, …). A separate request path from chat, with its own response
   shape and its own model list.
2. **A chat model that outputs images**, identified by `architecture.output_modalities`
   containing `image`. Same `/chat/completions` path we already use.
3. **A server-side tool**, `{ "type": "openrouter:image_generation" }` in the
   `tools` array, which works with **any** model — the model decides an image is
   wanted, OpenRouter generates it (default `openai/gpt-5-image`), and the reply
   contains an image **URL**, typically inline as markdown. This is the same shape
   of surprise as web search in M2.5: **not a model capability**, so gating it on
   the catalog would be wrong.

**Response payloads differ per route, and so does their lifetime.** Route 1 is
base64 bytes. Route 3 returns a URL that OpenRouter documents as **temporary** —
"download or cache it if you need it long-term". A conversation that is still
readable next month cannot rely on it.

**Image models describe their parameters in a different shape from chat models.**
Chat models carry `supported_parameters` as an array of strings, which is what
T1.7.2's schema and T1.7.7/T1.7.8's settings contract are built on. Image models
carry an **object of typed capability descriptors** —
`{ "resolution": { "type": "enum", "values": ["1K","2K","4K"] }, "seed": { "type": "boolean" } }`.
That is a richer shape than the settings picker was designed for, and it is the
answer to "what settings do image models take": read it, do not guess a list.

**`supports_streaming` is a per-model boolean on the image listing, and it can be
false.** "Show that an image is in progress" may therefore mean a placeholder with
no partial data to render, not a progressive image. Both cases probably need to
exist.

**The catalog may not even contain image models today.** `/api/v1/models` defaults
to `output_modalities=text`; the parameter accepts a comma-separated list or `all`.
We fetch `/models/user` (T1.7.1b), and the recorded fixture does contain entries
whose `output_modalities` are `["image","text"]` — but nothing yet proves an
**image-only** model such as `bytedance-seed/seedream-4.5` survives that endpoint's
default. **Check this first.** If they are filtered out, "filter by output" is not
a UI task at all; it starts at the fetch.

`architecture.output_modalities` is in the raw feed and in the fixture, but
`openrouter-catalog.ts` does not map it and `selectableModelSchema` has no field
for it. Both need it before any filter can exist.

## What the milestone covers

The user's list, with the dependencies found above folded in.

- **Choose the route.** Decide between the three above — possibly more than one,
  but deliberately. This gates everything else.
- **Output-modality filter in the picker.** The row already asks what a model
  _accepts_ (T1.7.4); it cannot ask what a model _produces_. Add the field to both
  schemas first. The existing filter row derives itself from the catalog and the
  "catalog must actually split on it" rule applies unchanged, so this should be
  one more entry rather than new machinery. **Note the plan already rejected an
  output filter once** — T1.7.4 records it as a no-op "because every one of our
  entries outputs text". That is exactly the assumption this milestone breaks;
  correct that paragraph rather than leaving it to contradict the code.
- **Render an image in a reply.** A new message part, alongside M2.5's citations.
  Decide base64-inline versus stored-and-referenced before writing the renderer.
- **Show generation in progress**, including the case where nothing partial ever
  arrives.
- **Preview, download, copy.** Copy needs verification, not assumption — writing
  an image to the clipboard is `ClipboardItem`, and Safari and iOS have real
  constraints on when it is allowed. Confirm on the target device.
- **Per-model image settings** in the settings picker (T1.7.8), driven by the
  descriptor shape above.
- **Storage and cost.** Both are new, and neither is optional:
  - A base64 PNG is orders of magnitude larger than a message row has ever been.
    Postgres column, object storage, or filesystem — decided with M2's schema in
    hand, not after.
  - Image pricing is not `prompt`/`completion` per token. T1.7.2 derives `isFree`
    from those two strings and the picker shows a per-million-token price; both
    are meaningless for a per-image charge and must not be shown as if they held.

## Open questions for the planning session

- **"Ensure caching is configured for available models" needs the user to say
  which cache is meant.** There are two: the catalog fetch's own TTL cache in the
  server, and M2.1's prompt caching. Neither obviously covers image models, and
  the answer changes which milestone owns it. Ask.
- Is image generation a mode the user picks (choose an image model), or something
  any conversation can do (the server tool)? This is the same question M2.5 asks
  about web search, and the two should probably be answered the same way — see
  that document's open question about where a non-per-model feature lives.
- Do generated images survive Mastra's stream and message layers, and in what
  shape? Verify against the installed packages. Do not assume.
- Is **image editing** — image in, image out — in scope, or a later milestone? The
  route-1 listing shows models whose `input_modalities` include `image`, so the
  capability is adjacent and cheap to reach for and easy to let sprawl.
- What does a refusal look like? Image generation is moderated more aggressively
  than text, and the failure path is unlikely to match T1.7.3's mid-stream error.
- What does a screen reader announce for a generated image, and what is its alt
  text when the only description available is the prompt?

## Definition of Done

To be written by the planning session. It must include the milestone verified on a
**phone-sized viewport**, not only a desktop one — the picker work in M1.7 was
signed off against mobile use, and an image preview is where that matters most.
