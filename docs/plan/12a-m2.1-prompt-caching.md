# M2.1 — Prompt caching (stub)

**Status:** not planned in detail. This document records why the milestone exists
and what is already known, so the session that plans it properly does not start
from scratch.

**Goal:** stop paying full input price for the conversation prefix that is resent
on every turn, on every provider that will cache it.

## Why it is after M2, not before

It was raised while M1.7 was in flight, with an open question about whether it
belonged at M1.9 or after M2. Three reasons put it after, all checked
against the live docs and the installed packages on 2026-08-03:

1. **Before M2 there is nothing to cache.** Caching pays for a long prefix that
   is stable across turns. Message history in this app is thread-scoped and
   arrives with M2 — `prepare-chat-request.ts` does not so much as mention
   `messages` today. A first turn writes a cache; there is no second turn to read
   it.
2. **The providers have minimums that a short chat never reaches.** Anthropic
   will not cache below 4,096 tokens on Opus 4.5–4.8 and Haiku 4.5 (1,024 on
   Sonnet 4/4.5/4.6 and Opus 4/4.1); Gemini 2.5 Pro needs 4,096 and Flash 1,024;
   OpenAI needs 1,024. Single-turn conversations sit under all of these.
3. **M2 decides what the prefix contains.** Working memory and semantic recall
   both inject content ahead of the user's message. Placing cache breakpoints
   before that exists means placing them twice.

That makes it M2.1: after M2, which it depends on, and **before** M2.5. There is
no dependency in that direction — web search does not need caching — but there is
one in reverse. Web search injects a block of results into the prompt on the turns
that use it. If those land ahead of the cache breakpoint, the prefix changes every
turn and nothing is ever read from cache, which is the same trap semantic recall
sets (see the open questions). Planning caching first means web search is designed
knowing where the breakpoint sits, rather than retrofitted around it.

## Known before planning starts

Verified against OpenRouter's prompt-caching documentation on 2026-08-03.

**Most providers need no code at all.** OpenAI, Grok, Moonshot, Groq, DeepSeek,
Z.AI and Gemini 2.5's implicit path all cache automatically with no request
changes. For those, this milestone is measurement and prefix hygiene, not
plumbing — keep the opening of the message array byte-stable and push variable
content toward the end.

**Three need to be asked explicitly**, all through
`cache_control: { type: 'ephemeral' }` on a content block: **Anthropic**,
**Alibaba Qwen** (a fixed list of models — snapshot endpoints are excluded), and
**Gemini's explicit path**. Gemini honours only the last breakpoint; Anthropic
allows at most four.

**Anthropic's automatic mode is one field, and it is the one we want.** A
top-level `cache_control` on the request body caches through the last cacheable
block and advances the breakpoint forward as the conversation grows. OpenRouter's
own docs call it "recommended for multi-turn conversations", which is exactly
this app's shape. Supported on the Anthropic, Vertex, Azure and Bedrock
providers. Prefer it over hand-placing per-block breakpoints.

**TTL is a decision, not a default.** 5 minutes is standard; `"ttl": "1h"` costs
2x on writes instead of 1.25x and only pays back across a long session. Which one
a chat app wants depends on how the user actually works, so measure before
choosing.

**Read multipliers, for judging what the milestone is worth:** Anthropic 0.1x,
DeepSeek 0.1x, Alibaba 0.1x, Gemini/Grok/Moonshot 0.25x, OpenAI 0.25–0.5x, Groq
0.5x, Z.AI ~0.2x. Write costs: free on Grok, Moonshot, Groq and Gemini implicit;
1x on DeepSeek; 1.25x on Anthropic, Alibaba and OpenAI from GPT-5.6 on.

**The catalog already carries the per-model signal.** `pricing.input_cache_read`
(183 of 337 models), `input_cache_write` (58) and `input_cache_write_1h` (21) say
which models cache and at what rate. T1.7.2's schema keeps only `prompt` and
`completion`, so widening it is this milestone's first schema change.

**Sticky routing is the hidden requirement.** A cache lives on one provider, so
OpenRouter pins follow-up requests to whichever provider served the cached one.
Stickiness works at two levels. **Implicit**: OpenRouter fingerprints the
conversation by hashing the first system message and the first user message, and
pins only _once a provider reports prompt cache usage_ — so it does nothing until
caching is already working. **Explicit**: a `session_id` (request body, or the
`x-session-id` header, max 256 characters) pins from the first successful
response. Either way the pin expires after **5 minutes of inactivity**, reset by
each successful request, and is not updated when the pinned provider errors, so
the next request can re-route. M2's thread id is the obvious `session_id`.

**That matters beyond caching.** With an auto-router as the default model, sticky
routing also pins the _resolved model_, not just the provider — OpenRouter's docs
are explicit that without it "you could get different models on each turn of a
conversation". That is a correctness problem wearing a performance problem's
clothes, and it is the strongest argument for not deferring this milestone much
past M2. Note the ordering trap: implicit stickiness only engages after cache
usage is observed, so on a model that never caches, the router is free to change
model every turn forever.

## Response caching is a different feature, and may land first

Verified 2026-08-04. OpenRouter also offers **response caching**: a whole
response replayed for a byte-identical request. It is unrelated to prompt caching
— it sits at the OpenRouter layer _before_ the provider, is model-agnostic, and
the two can be used together.

- Opt in per request with `X-OpenRouter-Cache: true`, or per preset with
  `cache_enabled`. Off by default.
- The cache key is API key + model + endpoint type + streaming mode + a SHA-256
  of the **normalised request body**. Whitespace does not matter; **JSON property
  order does**, and so does sending a default explicitly rather than omitting it.
- Hits are **free** — every usage counter is zeroed, and they do not touch
  provider rate limits. `X-OpenRouter-Cache-Status: HIT|MISS` says which happened.
- TTL 1–86400s, default 300. `X-OpenRouter-Cache-Clear: true` refreshes one entry.
- Streaming is supported; the cached stream is replayed through the same pipeline.
- Unavailable under account-level ZDR. No request coalescing: two identical
  in-flight requests both miss and both bill.

**For a chat app the production value is near zero** — real conversations are
never byte-identical. The value is in the **test suite**: OpenRouter names
repeatable test responses as a use case, and it would let an integration test hit
a real model once and replay it free thereafter. That is a testing-strategy
decision (`03-testing.md`) with no dependency on M2, so it could be pulled
forward independently of everything else in this milestone. It does not change
the mocking rules — a replayed real response is still a real response.

**It is measurable, so measure it.** Every response carries
`usage.prompt_tokens_details.cached_tokens` and `cache_write_tokens`, plus a
`cache_discount` field. A before/after number belongs in the Definition of Done —
this is a milestone whose entire value is a cost curve.

## Open questions for the planning session

- **Can these fields be set at all through Mastra?** This is the one that decides
  the shape of the milestone. `@mastra/core` documents
  `providerOptions: { anthropic: { cacheControl: … } }` at the instruction level,
  but top-level `cache_control` and `session_id` are request-root fields, and
  every request here goes through the `openrouter/` model router rather than a
  provider SDK directly. Verify against the installed packages before assuming an
  escape hatch exists. If there is none, finding or building one is task one.
- M1.7 observed that `providerOptions.anthropic` survives the trip through
  OpenRouter for thinking. That is an observation about one field, not proof the
  mechanism generalises.
- **Does semantic recall defeat caching?** Recall injects retrieved messages that
  differ per turn. If they land before the breakpoint, the prefix changes every
  turn and nothing is ever read from cache. This may constrain how M2's memory is
  ordered, which is a reason to plan the two together even though they ship apart.
- Is any of it user-visible? Probably not — but a saving nobody can see is also a
  saving nobody can confirm, so decide deliberately rather than by omission.
