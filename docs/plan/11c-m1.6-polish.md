# M1.6 — Thinking on Demand, and Two Composer Annoyances

**Goal:** Make extended thinking a per-request choice the user makes, not a property
of the model they picked — and fix two things about the composer that are wrong every
single time it is used.

**Why it exists:** M1.5 gave the composer a model picker, and M1 gave it a reasoning
pane that renders whatever the model streams. Neither gave the user any say in
_whether_ the model thinks. The obvious implementation — "Opus thinks, Haiku does
not" — bakes a cost and latency decision into the model list, where it cannot be
changed for a single question. Asking Sonnet a throwaway question should not cost a
thinking budget, and asking it a hard one should not require switching models.

**Size:** small. Three tasks, all of them adjustments to code that already exists. It
sits before M1.5's remaining E2E work only because the reasoning toggle changes the
request body that T1.5.5's scripted model will be asserting against — settle the
shape first, script against it once.

---

## Tasks

### T1.6.1 — Thinking is a toggle, not a model property

**The rule: no model thinks by default, and any model that _can_ think must be able
to answer without thinking.** The same id — `anthropic/claude-sonnet-4-6` — must be
usable both ways, chosen at send time. Do not add "Sonnet (thinking)" as a second
entry in the allowlist; that is the same defaulting mistake wearing a disguise.

- **Capability, not configuration.** The allowlist entry gains a flag saying whether
  the model _supports_ extended thinking. It says nothing about whether thinking is
  on. The picker and the toggle read it; nothing else does.
- **Do not invent the flag's value.** Which Anthropic models support extended
  thinking is a fact about the provider, not a guess. Confirm each one before marking
  it, and if a model's support cannot be confirmed, mark it unsupported — the failure
  mode of a wrong `true` is a rejected request on every send.
- The toggle lives in the composer footer, beside the model picker. It is **off by
  default**, for the same reason the picker defaults to the cheapest model: an
  accidental send should cost the least.
- Selecting a model that cannot think disables the toggle and forces it off. Coming
  back to a thinking-capable model must not silently restore a state the user cannot
  see — decide the behaviour and make the control's appearance match it.
- Like the model choice, the toggle travels **per message** in the request body, and
  persists across sends and reloads in browser storage. Per-thread persistence is an
  M2 question. Do not build it here.
- **The server decides what the flag means.** The client sends a boolean; it must
  never send a token budget, a provider options object, or anything else the provider
  API would accept verbatim. Translating "thinking: true" into provider options is
  the server's job, exactly as model resolution is — the same reasoning as M1.5's
  T1.5.2, and for the same reason.
- Validate it in the chat route's existing middleware, alongside `model`. Thinking
  requested on a model that does not support it is a 400, not a silently dropped
  field. A request that omits the flag is a request that does not want thinking —
  this is the one place a default is correct, because `false` costs nothing.
- **Read the embedded docs before writing the provider call.** `@ai-sdk/anthropic` is
  not a direct dependency; models are resolved through Mastra's registry by
  `provider/model` string, so the mechanism for passing provider-specific options is
  Mastra's, not the AI SDK's directly. Start at
  `node_modules/@mastra/core/dist/docs/references/` — `reference-agents-stream.md`
  for the per-call options, and search the reference folder for `providerOptions`.
  Write nothing about thinking parameters from memory.
- The reasoning pane already exists (`ReasoningPart.svelte`) and renders whatever
  reasoning parts arrive. Expect to change **nothing** in it. If it needs changes,
  that is a finding worth logging, not a licence to redesign it.
- Tests: the flag survives the proxy hop unchanged; thinking on an incapable model is
  rejected; an absent flag means no thinking rather than an error; the toggle
  disables and clears when an incapable model is selected; two sends with the toggle
  in different positions carry different bodies.

**Verify by hand, in a browser:** ask the same question twice on one thinking-capable
model, toggle off then on. The first answers directly; the second shows the thinking
pane. That is the whole point of the milestone — a screenshot of one of them proves
nothing.

### T1.6.2 — A quieter focus ring on the composer

The global `:focus-visible` rule in `layout.css` puts a 2px accent outline with a 2px
offset on everything. On the composer's textarea — which is already a large bordered
box — that reads as a heavy blue frame around the biggest element on screen, every
time the user clicks into it, which is constantly.

- The wanted effect is Claude's: the input's own border becomes subtly brighter to
  show it is focused. A hint, not an announcement.
- Apply it to the composer's **wrapper**, not the textarea, so the whole input block
  responds as one object. The textarea already has `outline-none`; the wrapper is
  what carries the visible border.
- Use `:focus-within` so the border stays lit while the user is inside the input, and
  keep the transition consistent with the rest of the app's hover transitions.
- **Do not weaken the global `:focus-visible` rule.** It is what makes keyboard
  navigation usable across every button and link, and this complaint is about one
  oversized box, not about focus indication in general. Scope the change.
- **Keyboard focus must remain obvious.** Tabbing to the composer has to be visible
  to someone who is not looking for it. If the subtle border alone fails that, say so
  and propose the compromise rather than shipping a quieter but unusable version.
- This is a user-visible aesthetic change. Show it before considering it settled.

### T1.6.3 — Clicking the composer's empty space focuses the input

The footer row holding the model picker and the send button is mostly empty space,
and it sits inside what looks and behaves like one input field. Clicking that space
does nothing, which makes the box feel dead in exactly the place a user is most
likely to click.

- Clicking anywhere in the composer's chrome that is not itself interactive should
  focus the textarea and place the caret at the end of the text.
- **The existing controls must be untouched.** The model picker opens, the send
  button sends, the stop button stops — none of them may also focus the textarea or
  swallow their own click. Verify each one still works, by clicking it.
- Prefer letting the real controls handle their own events over hand-written target
  sniffing. A check that asks "was this click on the empty part" by inspecting the
  event target is fragile the moment a control gains an icon or a nested span.
- **Do not make the wrapper a button or give it a click handler that traps keyboard
  users.** The textarea is already reachable by keyboard; this is a pointer
  affordance only, and it must not add a tab stop, an ARIA role, or a second way to
  do what Tab already does.
- Tests: clicking the footer's empty space focuses the textarea; clicking the send
  button sends without stealing focus; clicking the model picker opens it and leaves
  the textarea unfocused.

## Definition of Done

Performed manually in a browser:

1. The composer footer has a thinking toggle, off on first visit.
2. One thinking-capable model, same question twice, toggle off then on → the first
   answers directly, the second shows the reasoning pane.
3. Selecting a model that cannot think disables the toggle.
4. Reload → both the model and the toggle position are as they were left.
5. Curl the proxy asking for thinking on an incapable model → rejected, readable
   error, no upstream call.
6. Focusing the composer shows a subtle border change, not a heavy outline — and
   tabbing to it is still unmistakable.
7. Clicking the footer's empty space focuses the textarea; the picker, send and stop
   buttons all still do their own jobs.
8. `bun run verify` passes, including coverage thresholds.

## Notes for the executing agent

- **The whole milestone is about not defaulting things on the user's behalf.** If an
  implementation choice would make thinking implicit — a model that always thinks, a
  budget the client cannot influence, a toggle that hides itself — it is wrong even
  if it works.
- Do not build a thinking-budget slider, a reasoning-effort dropdown, or a token
  display. A boolean is the whole feature. If the budget turns out to need tuning,
  that is a constant on the server, not a control.
- T1.6.2 and T1.6.3 touch the same component and are both user-visible. They are
  separate tasks, and each ends green on its own.
